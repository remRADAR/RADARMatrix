## M2.2.1 OUTCOME (`security/m2-2-hardening` — same branch, corrections of the M2.2 review findings)
- **A — Grant integrity is now KEYED:** the M2.2 unkeyed sha256 seal could be recomputed by anyone able to mutate both the grant and its hash. Correction: `createGrantIntegrityService(secret)` — a server-held HMAC-SHA-256 service (secret ≥ 32 chars or the service is null; the secret NEVER appears in grants, request data, results, errors or logs). The seal uses deterministic canonical serialization and binds EVERY authority-bearing field: grant id, actor id, agent id, workspace, tools, actions, expiry, max uses AND current uses. `validateGrantUse`/`reserveGrantUse` recompute the seal with `timingSafeEqual` BEFORE any policy check; recomputed UNKEYED hashes fail (`grant_mutated`); missing/short/absent secret fails closed (`integrity_unavailable`) — there is NO unkeyed fallback. Trade-off recorded: an immutable server-side grant record was considered and DEFERRED to the durable store (D1, M7) to preserve the existing grant contract.
- **B — Grant-use enforcement is now ATOMIC:** the M3 flow validated a grant, performed the GitHub request, then recorded the use — two concurrent requests could both pass validation. Correction: `reserveGrantUse(grant, integrity, now)` is a synchronous check-and-consume (seal check → expiry → capacity → increment `uses` → RE-SEAL) executed BEFORE dispatch. Two simultaneous requests against one remaining use: exactly one reserves. A rejected reservation never dispatches. Reservations are NOT refunded on transport failure/timeout/cancellation/uncertain outcomes (documented policy — refunding enables over-use). Reservation state cannot be reset by caller mutation (`uses` is HMAC-sealed). HONEST LIMIT: per-process atomicity only — this is NOT a distributed lock; cross-process capacity requires the durable store (D1, M7). `recordGrantUse` is REMOVED (documented contract change); the M3 branch still imports it — its compatibility adapter on this branch carries the migration, the original M3 branch is untouched.
- **C — Trusted-actor provenance is now RUNTIME-enforced:** the M2.2 `TrustedActorContext` was a plain TypeScript interface — a caller could construct one with fabricated admin roles. Correction: the context is branded with a module-private `Symbol` and minted ONLY by `createTrustedActorContext(principal, membership)`, which verifies workspace membership via the trusted membership layer and derives the role from it. `deriveActorAuthority` and `createDelegatedGrant` enforce the brand AT RUNTIME (the compile-time type is never the boundary). Caller-supplied `actor_roles`/`actor_tools`/`actor_can_write` remain rejected outright; cross-workspace and unauthenticated actors fail closed; delegation can never grant authority the actor does not possess. (M2.2.2 residual closed: the PROVIDER and the REGISTRY are now server-bound at the composition boundary — see the M2.2.2 OUTCOME.)
- **D — Approval ordering and replay (M3 flow):** the M3 adapter redeemed an approval BEFORE validating the delegated grant — an invalid grant could consume a valid approval. Correction in the compatibility adapter on this branch: grant integrity/actor/agent/workspace/scope/expiry/capacity validation → `reserveGrantUse` → approval redemption (exact binding: action, resource, workspace, actor, grant) → dispatch. A failed grant check never consumes an approval; a failed approval check never dispatches. `approvals.ts` itself needed NO change (its internal order and atomic `claim()` were already correct). Single-use is atomic per process; cross-process single-use requires the durable store (D1, M7) — stated, not claimed.
